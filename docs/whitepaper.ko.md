## 초록

[OpenClaw](https://docs.openclaw.ai) 에이전트의 장기 기억을 마크다운 볼트로 두고,
OpenClaw 내장 기억 검색(로컬 임베딩, SQLite FTS5, 하이브리드 랭킹)으로 색인해 씁니다.
이 기억을 잴 수 있게 하려고 튜닝 전에 25문항 평가셋을 고정해 두고, 2026년 8월부터
11월까지 한 회차에 한 가지만 바꾸며 45회차(보조 회차 6개 별도)를 돌렸습니다.

주요 결과:

- **코퍼스 구조가 지배했습니다.** 지식을 개념당 큐레이션 노트 하나로 나누자 근거 문서
  적중률이 한 회차에 40% → 88%(+48%p)가 됐습니다. 검색기 쪽 어떤 변경도 근처에 못
  갔습니다.
- **그 뒤의 지배 변수는 칸 점유였습니다.** 한 파일이 질의당 상위 5칸 중 2.03칸을 먹을 때
  84%, 1.33칸일 때 92%.
- **랭킹 손잡이는 상수입니다.** 배포된 검색 함수로 만든 오프라인 복제가 세 판에서
  라이브 결과를 칸·순서까지 재현했습니다(2026.9.7 85/85칸, 2026.10.5·2026.10.9 66/66문항).
  혼합 가중치·MMR·30일 감쇠가 상수로 박혀 있고, 17문항 탐침에서 항상 켜진 두 단계의
  대가는 약 3문항과 MRR 의 3분의 1 이었습니다.
- **나이를 먹는 것은 큐레이션 노트뿐**이라, 그 나이를 고정한 것이 2026.9.7 에서 가장 큰
  손잡이였습니다. 원 문항 44% → 92%(그 회차엔 변수 다섯이 함께 움직임).
- **그래프 자체의 검색 효과는 입증되지 않았습니다.** 사전에 정한 판정으로, 타입 링크를
  빼도 multihop 이 떨어지지 않았습니다.
- **2026-11-03 이후:** 고정 기준선 회귀 점검(31/38, 연속 측정 흔들림 0문항), 문서 정리
  뒤 낡은 값 탐침에서 1위 청크가 옛값인 문항 15개 중 7 → 4, 줄 안 정정 표지로 「정정 없이
  옛 주장만 돌아온 질의」 20개 중 4 → 0, 그리고 2026.10.9 복제 재검증에서 감쇠가 파일의
  현재 mtime 을 읽는다는 것을 확인했습니다.

모두 n = 1 입니다. 코퍼스 하나, 임베딩 모델 하나, 문항과 노트를 같은 사람이 썼습니다.
방향은 옮겨 쓸 수 있고 숫자는 우리 것입니다.

## 1. 배경과 문제

에이전트는 매일 운영 업무에 쓰입니다. 기억 계층은 세 부분입니다.

1. 매 턴 주입되는 루트 메모(수천 자),
2. 에이전트가 쓰는 날짜별 일일 메모,
3. 큐레이션 노트: 부품·프로젝트·사건·교훈마다 노트 하나, 소수의 타입 술어로 연결
   ([부록 B](ontology-schema.md)).

루트 메모를 뺀 나머지는 `memory.search` 를 통해서만 모델에 닿고, 이 검색은 상위 k
청크를 돌려줍니다(우리 설정 k = 5). 실제 질문은 이것이었습니다. **에이전트가 적어 둔
사실이 필요할 때, 그 노트가 상위 5에 돌아오는가?** 2026년 8월 전에는 이를 답할 방법이
없었고 튜닝 주장은 전부 일화였습니다.

방법을 정한 두 성질:

- 검색 결과는 공유된 창입니다. 한 문서를 올리는 변경은 무관한 질의에서 다른 문서를 밀어낼
  수 있으니, 변경은 전체 문항으로만 판정할 수 있습니다.
- 랭킹 코드는 에이전트 판올림마다 바뀌고 코퍼스는 매일 바뀝니다. 숫자는 같은 판·같은 측정
  경로 안에서만 비교할 수 있습니다.

## 2. 시스템 구조

```
질문
   │
   ├─ 벡터 검색   로컬 llama.cpp 서버 · embeddinggemma-300m (768차원)
   └─ 텍스트 검색 SQLite FTS5 (unicode61), 키워드 대체 채점기 포함
   │
   ├─ 하이브리드 0.7 / 0.3  →  시간 감쇠(반감기 30일)  →  MMR (λ 0.7)
   │      ↑ 잰 모든 판(2026.10.9 까지)에서 셋 다 상수
   ▼
상위 k 청크 → 에이전트 컨텍스트
```

| 계층 | 선택 | 이유 |
|---|---|---|
| 임베딩 | 로컬 `llama.cpp` 관리형 서버 | 키 없음·만료 없음·오프라인 동작. 상주 약 95MB |
| 색인 | 에이전트 DB 옆 SQLite (FTS5 + 벡터 테이블) | 백업할 파일 하나, 스냅샷 가능 |
| 청킹 | 400토큰 / 겹침 80 | 제품 기본값. 청크 크기보다 파일 **모양**이 중요했음 |
| 코퍼스 | 경로 허용목록으로 색인한 마크다운 볼트 | 평문·diff 가능·사람이 고칠 수 있음 |
| 온톨로지 | 노트 사이 타입 링크, 술어 최대 8개 | [부록 B](ontology-schema.md) |

**랭킹 파이프라인(배포 코드에서 읽고 복제로 확인, §3.6).** k = 5 여도 벡터 후보 200개와
키워드 후보 200개를 뽑아 0.7 / 0.3 으로 섞고, 시간 감쇠를 걸고, MMR 을 돌린 뒤 k 개로
자릅니다. 이 파라미터들에는 설정 칸이 없습니다. 한국어 문장 질의는 FTS5 경로(모든 낱말
AND)가 대개 0건이라 대체 키워드 채점기가 돌고, 17문항 탐침에서 키워드 후보 200개 중
중앙값 169개가 최대 점수에 붙어 순서는 사실상 벡터 유사도가 정했습니다.

**감쇠 시각의 출처.** 날짜 이름의 일일 메모는 파일명 날짜로, 루트 메모와 기억 폴더의
날짜 없는 파일은 면제, 그 밖의 파일(실제로는 큐레이션 노트)은 수정 시각으로 나이를
먹습니다(2026.10.9 에서는 검색 시점의 파일 현재 mtime, §4.5).

**코퍼스 구성.** 2026년 9월 청크의 약 56% 가 큐레이션 노트, 39% 가 자동생성물, 5% 가
루트 메모였습니다(1,640청크 / 285파일). 11월 초 색인은 6,059청크 / 1,092파일이고 구성은
다시 재지 않았습니다.

## 3. 방법

실패한 부분까지 포함한 상세는 [부록 A](evaluation-method.md) 에 있습니다.

### 3.1 평가셋

튜닝 전에 썼습니다. 문항마다 답에 닿으려면 상위 k 에 반드시 있어야 하는 문서를 적어
둡니다. 채점은 기계적입니다. 기대 문서가 상위 5에 있거나 없거나. 답변 문장은 채점하지
않습니다.

| 종류 | n | 잡는 것 |
|---|---|---|
| `fact` | 8 | 적힌 값을 아예 찾을 수 있는가 |
| `multihop` | 9 | 함께 봐야 하는 두 문서 |
| `causal` | 8 | 원인. 대개 증상과 다른 노트에 있음 |
| `negative` | 5 | 좋은 답이 없는 질문에 무엇이 자신 있게 답하는가 |
| `recency` | 6 | 최근 일. 최신성 가산의 값을 잼(따로 보고) |

대표 수치는 자동채점 25문항(`fact` + `multihop` + `causal`)입니다. `recency` 와
`negative` 는 옆에 따로 적고 합치지 않습니다. 42회차부터 `negative` 는 검색 층에서
반자동으로 판정합니다(상위 5청크 중 전제 낱말을 모두 담은 청크가 있는가). 환각 측정은
아닙니다.

9월 말부터 점유 탐침(17문항, 54문항 중 49 자동채점)을 더해 k = 5·6·20 에서 읽고, 놓친
답이 창 밖 얼마나 먼 곳에 있는지 봅니다.

### 3.2 회차당 한 가지, 전 문항 재측정, 기록은 색인 밖

회차마다 하나만 바꾸고 모든 문항을 다시 돌립니다. 점수를 잃은 회차도 전부 기록합니다.
회차 기록은 **색인된 코퍼스 밖**에 둡니다. 색인 안에 둔 결과 기록이 41청크로 불어나
정답을 밀어낸 일이 있었습니다(§4.7).

### 3.3 보류셋과 은퇴 문항

10월 말에는 원 25문항 대부분이 한 번 이상 수정의 목표가 됐기 때문에, 이제 회귀 감시용일
뿐 변경 효과의 근거가 아닙니다. 문항을 *사용됨*(수정을 이끈 적 있음), *천장 근처*,
*보류*로 나눕니다. 보류셋(`holdout_v1`)은 15문항(13 자동채점)이고 색인 밖에 두며 내용
해시로 고정하고 하네스가 import 로 읽습니다. 무언가를 고치다 보류 문항을 보면 그 문항은
*사용됨*으로 옮기고 새 문항으로 채웁니다. n = 13 이라 2문항 이상 차이만 신호로 보고,
보류셋은 변경마다가 아니라 주 1회 잽니다.

### 3.4 고정 기준선 회귀 점검 (2026-11-08 추가)

회차 러너는 매 회차를 직전 정상 회차와 비교합니다. 이러면 회귀가 한 번에 한 문항씩 새어
들어와 문턱에 한 번도 안 걸릴 수 있습니다. 회귀 점검은 **고정 기준선**과 비교합니다.

- 점수 = 원 25 + 보류 13 = 38점. `recency` 와 `negative` 는 곁 지표.
- 기준선은 연달아 두 번 잽니다. 문턱 = max(1, 두 측정의 점수 차, 결과가 갈린 문항 수).
  두 측정 사이 뒤집힌 문항은 흔들림으로 표시해 「새 놓침」에서 뺍니다.
- 판정: 점수가 2 이상 떨어지거나 안정 문항 2개 이상을 새로 놓치면 **회귀**(종료코드 2).
  안정 문항 새 놓침 1개는 주의.
- 먼저 건강 게이트를 돌립니다. 51질의 중 5% 넘게 결과 0건·오류·타임아웃이면 점수를 내지
  않습니다(종료코드 3).

검색 층만 잽니다. 지시문 문구를 고쳐 생기는 행동 회귀는 범위 밖입니다.

### 3.5 낡은 값 탐침 (2026-11-07 추가)

원 문항은 「맞는 문서가 상위 5에 있는가」를 묻습니다. 다른 실패는 못 봅니다. 맞는 문서는
돌아오는데, 돌아온 청크(또는 그 위 청크)가 이제는 사실이 아닌 값을 말하는 경우입니다.
탐침은 이렇습니다.

- 값이 바뀐 것으로 아는 사실 15개(소프트웨어 판, 설정값, 스케줄러 상수, 기기 설정).
  값 낱말을 넣지 않은 질문을 검색 전에 고정합니다.
- 각 사실의 현행값은 파일이 아니라 실제 시스템에서 읽습니다.
- 상위 5청크 75개를 사람이 전문으로 읽어 *옛값*, *현행값*, *전→후*(한 청크에 둘 다),
  *무관*으로 표시합니다. 제안·가정 문장 속 값은 세지 않습니다.
- 보고 항목: 상위 5에 어떤 표시가 있는가, 1위 청크의 표시, 값을 처음 담은 청크의 표시,
  정본 노트가 상위 5에 들고 현행값을 담는가.
- 변형으로, 옛값을 전제로 깐 질문 5개를 따로 묻습니다.

15개 사실은 값이 바뀌었기 때문에 고른 것이라, 숫자는 코퍼스의 낡음 비율이 아니라 사례
수입니다.

### 3.6 오프라인 복제 하네스

랭킹 상수를 설정으로 못 바꾸니 「만약에」 질문 대부분은 오프라인에서만 답할 수 있습니다.
색인을 읽기 전용으로 복사하고, 배포된 검색 함수를 import 하고, 질의를 재생하며 한 단계씩
바꿉니다. 복제는 다음을 통과한 뒤에만 믿습니다.

1. 모든 문항에서 라이브 상위 k 와 **순서까지** 같다. 판올림마다 다시 확인.
2. 일부러 망가뜨리면(질의 접두어 빼기, 감쇠 시계 옮기기, MMR 끄기) 일치가 무너진다.

### 3.7 관리하는 하네스 위험

- **측정 경로.** 락을 잡는 CLI 경로는 일부 질의에 약 52초 정지를 더했고, 같은 질의가
  서비스 API 로는 약 1초였습니다. 경로를 결과 파일마다 찍고 지연은 경로를 넘어 비교하지
  않습니다.
- **회차 번호.** 회차 번호는 돌릴 때 매깁니다. 늦게 기록한 6회차는 시각순으로 36-1 …
  36-6 보조 회차로 넣었습니다.
- **원인을 지목하기 전에 회차 사이 바뀐 것을 셉니다**(직전 결과 파일 기준 `find -newer`).

## 4. 결과

OpenClaw 판이 다른 숫자는 비교하지 않습니다. 판: 1–6회차는 2026.8.2 이전 판,
7–24 2026.8.2, 25–37 2026.9.2,
38–39 2026.9.7, 40 2026.10.5, 41부터 2026.10.9. 42·43회차는 측정기를 바꿔 새 비교점이
됩니다.

> 고친 규칙: 파일이 아니라 색인이 쓴 시각을 확인할 것.

> 만 바꿔도 순위가 움직입니다. 그러니 이 규칙은 판에 따라 다릅니다. 쓰는 판이 어느 시각을

### 4.6 그래프 자체가 검색을 돕는가? 입증 안 됨 (H)

측정 전에 판정 기준을 커밋했습니다. **타입 링크가 검색을 돕는다면 빼면 `multihop` 이
떨어져야 한다.**

| 팔 | 변경 | 원 25 | multihop |
|---|---|---|---|
| A | 현행 | 84% | 9/9 |
| B | 술어 줄과 자동 역링크 블록 제거(코퍼스 6.75%) | 96% | 9/9 |
| C | 자동 역링크 블록만 제거(3.85%) | 84% | 8/9 |

`multihop` 이 안 움직였으니 사전 판정으로 그래프의 검색 기여는 입증되지 않았습니다.
B 의 +12%p 는 예상 밖이었고, C 팔이 「부피가 줄어 재배열됐다」는 설명을 배제합니다.
남은 추측(반복되는 술어 줄이 노트 사이 구별 신호를 흐린다)은 복제에서 상투적 술어 줄
316개를 지워도 아무 변화가 없어 약해졌습니다. A1 을 지금은 이렇게 읽습니다. 검색을
움직인 것은 개념당 이름 잘 붙은 노트 하나로 나눈 구조이고, 타입 링크는 사람에게 감사
구조로서 쓸모가 있습니다.

돌아온 9개 질의는 모두 그 청크 안에 표지를 담고 있었습니다. 순위는 내려가지 않았습니다
(예: 1위 0.762 → 0.780). 표지는 노출을 줄이는 게 아니라 정정이 주장과 함께 따라오게
합니다. 루트 메모를 포함하지 않는 다른 에이전트 색인 두 곳에 같은 20질의를 돌려도 정정
없는 경우는 0이었습니다.

## 5. 한계와 반증

### 5.1 한계

- **n = 1.** 코퍼스 하나, 사람 하나, 임베딩 모델 하나.
- **사각지대.** 기대 문서가 전부 큐레이션 노트라, 원본 일일 메모에만 있는 지식을 잃는
  조치는 무해한 것으로 채점됩니다.
- **채점 안 된 문항.** 30문항 중 `negative` 5문항은 41회차까지 채점되지 않았고, 42회차부터
  검색 층 대리 판정이 돕니다. 답변 층 환각은 재지 않습니다.
- **원 25문항은 이미 가르친 문항입니다.** 효과는 보류셋으로 잽니다.
- **답이 아니라 검색.** 낡은 값 탐침과 정정 표지 측정은 무엇이 검색되는지를 잽니다. 답변
  모델은 날짜 표지를 보고 낡은 청크를 거를 수도 있습니다. 도구는 약 700자 스니펫을 주고,
  일부 경우 현행값이 스니펫 밖에 있었습니다.
- **고른 탐침.** 낡은 값 사실과 정정 표지 질의는 우리가 골랐습니다. 사례 수로 읽으십시오.
- **판올림은 랭킹 코드를 바꿉니다.** 판올림마다 새 기준선입니다.
- **시험 안 된 갈래.** 2026.10.9 의 importance·project-key 랭킹 갈래는 우리 색인에 데이터가
  없어(6,214행 중 0) 복제에서 시험되지 않았습니다.

## 6. 재현 방법

### 6.1 이 리포의 도구

- [`tools/index_census.py`](../tools/index_census.py): OpenClaw 기억 색인의 총 청크 수,
  파일 수, 파일별 청크 점유. 한 파일이 상한(기본 6%)을 넘으면 종료코드 1.

  ```
  python3 tools/index_census.py --top 20 --limit 0.06
  ```

- [`tools/evalset_run.py`](../tools/evalset_run.py): 회차 러너. `QUESTIONS` 를 본인
  문항으로 바꾸면 됩니다. 게이트웨이로 `memory.search` 를 부르고, stderr 를 잡고, 측정
  경로를 찍고, 회차마다 JSON 파일 하나를 씁니다.

  ```
  python3 tools/evalset_run.py 1
  ```

SQL 로 직접 보려면:

```sql
SELECT path, COUNT(*) c,
       ROUND(100.0*COUNT(*)/(SELECT COUNT(*) FROM memory_index_chunks),2) pct
FROM memory_index_chunks GROUP BY path ORDER BY c DESC LIMIT 20;
```

### 6.2 설명만 하고 싣지 않은 절차

회귀 점검, 낡은 값 탐침, 복제 하네스는 우리 폴더 구조와 설치된 OpenClaw 판 내부의 해시
모듈 이름에 묶여 있어 싣지 않고 설명만 합니다. 복제를 직접 만들려면:

1. 읽기 전용 연결에서 SQLite backup API 로 색인을 복사합니다. 라이브 파일을 쓰기로 열지
   않습니다.
2. 설치된 `dist/` 에서 배포 검색 모듈을 내보내기 이름으로 찾습니다(파일명은 내용 해시라
   판마다 바뀝니다). 로컬 임베딩 서버의 포트도 찾습니다.
3. 고정 질문 목록을 라이브 `memory.search` 와 복제에 모두 재생하고, 모든 문항에서 상위 k
   순서가 같아야 합니다.
4. 일부러 망가뜨려(질의 접두어, 감쇠 시계, MMR) 일치가 무너지는지 봅니다. 판올림마다
   2–4 를 다시 합니다.

### 6.3 첫날부터 한다면

1. 평가셋부터 씁니다. 25문항이면 충분합니다.
2. 파일별 청크 점유 계기를 붙입니다.
3. 긴 색인 문서보다 개념당 이름 잘 붙은 노트 하나를 택합니다.
4. 자동생성물과 측정 기록은 색인 밖에 둡니다.
5. 회차당 하나만 바꾸고 전부 다시 돌립니다.
6. 판올림마다 새 기준선을 잡고, 배포된 랭킹 코드를 읽습니다.
7. 수정을 이끈 문항은 은퇴시키고, 보류셋과 고정 회귀 기준선을 둡니다.
8. 정정 표지는 고치는 줄 안에 넣고, 값 표의 날짜 표지는 값과 같은 청크 안에 둡니다.
